# 应用市场审核修复与复核

对应审核条款：[4.3.1 权限与访问控制](https://docs.halo.run/developer-guide/app-store/app-review-guidelines#431-权限与访问控制)。

## 修复边界

- 个人中心列表在数据库分页前使用 `username + subject + 未撤销 + 未删除` 查询，分页总数也不能泄露旧账户授权数量；撤销操作采用相同归属校验。
- `subject` 绑定用户名和账户创建时间。重试、授权写入和授权确认会话都保留原账户身份，不能因同名重建而切换到新账户。
- 新授权名称包含 `subject`。旧版按用户名命名的记录只可由原账户复用，重建账户不会覆盖它。
- `UserAuthorizationCleanup` 在用户创建和已有用户调谐时添加 Finalizer；写入授权前也确认保护已持久化。用户删除后分批清理授权、授权码、令牌和令牌族，等待实际删除完成再移除 Finalizer。清理失败保留保护并重试。
- `ConsentCleanup` 在插件启动及授权变化时清理无主、删除中或账户身份不匹配的授权；接口的身份隔离不依赖后台任务执行时机。
- 停用时释放本插件的 Finalizer，并保留其他插件的 Finalizer；再次启用时恢复保护和历史记录清理。

- `UserAuthorizationCleanupTest`：旧用户授权、签发令牌、删除、等待实际清理、同名重建；新用户列表为空、旧记录撤销返回 404、旧令牌不可用、新用户可重新授权。
- 同一测试类另覆盖遗留旧版记录、清理失败重试、超过一批的已撤销记录、停用释放保护和无主记录清理。
- `OidcAuthorizationControllerTest`：原账户打开授权页后，同名新账户不能提交该页面。
- `OidcSecurityTest`：授权码单次消费、PKCE、密钥、刷新轮换及重放、角色移除、撤销、签名与声明、服务开关等既有回归。

测试存储模拟 Halo 的删除标记、Finalizer 和异步 GC，不把发出删除请求等同于数据已删除。构建报告位于 `build/reports/tests/test/index.html`。

## 人工复核步骤

以下步骤须由开发者实际执行并确认；自动化测试和 AI 代码走查不能替代人工审查。请在独立测试实例和专用测试账户中进行。

1. 安装本次构建的 JAR，确认插件启用、Discovery 与应用列表端点正常。创建测试用户 `oidc-review-user` 和独立示例应用，按 README 的 Node.js 示例完成一次登录授权与刷新。
2. 用测试用户进入个人中心，记录授权名称、范围和时间，确认能撤销自己授权；重新授权，为删除测试保留记录。用另一用户尝试撤销此记录，应返回 404。
3. 管理员删除测试用户。用户处于删除中时不能再登录或获取 OIDC 身份；同名创建应被拒绝，直到关联记录实际清理完毕且旧用户消失。
4. 使用管理员权限检查 `OidcConsent`、`OidcAuthorizationCode`、`OidcToken`、`OidcTokenFamily` 中该用户名的记录均已清理。管理员可以查询资源 API 的 `fieldSelector=spec.username=oidc-review-user`；个人用户不应获得这些原始资源的权限。
5. 创建相同用户名的新账户并重新登录。个人中心列表应为空；对旧授权名称调用撤销接口应为 404；原访问令牌、刷新令牌及未使用的授权码应失效。新账户重新授权后可以查看和撤销新授权，`sub` 与旧账户不同。
6. 测试登录后无应用角色时的权限提示、取消授权、同意后回调、未登录跳转、公开客户端强制 PKCE、机密客户端有/无 PKCE，以及刷新重放后的失效行为。
7. 停用插件后，用户删除不应被本插件的 Finalizer 卡住。再次启用，确认残留旧授权被清理、既有有效账户仍能使用自己的授权。
8. 人工审阅本次接口过滤条件、账户 `subject` 计算、Finalizer 生命周期、版本冲突重试、删除确认和凭据输出，确认符合实际部署方式。
